# camelFS v0: the limitations ledger

Miguel, 2026-11-12: "document every limitation or shortcoming or slowness that we encounter for this V0 … on V1 we
address all of these." This is that list, one entry per limitation, kept current as Prototype v0
([camel-fs.md](camel-fs.md) §4) is built and used. Every entry has an id, the area it lives in (`daemon`
`camelfsd`; `jobhost` the TypeScript host agent; `guest` `camel-guest`; `runtime` the Workers/Node backend; `API`
the file API tier and its clients; `S3`; `ops`), what it is, the measured impact with numbers and where they came
from, why v0 accepts it, the v1 fix, a **scope** and a status (`open` or `fixed`, with the PR when fixed). The
scope carries Miguel's later rule (2026-11-12): **well-scoped limitations are fixed as we find them, not deferred to
v1**; the ledger stays the full record either way. `small` means fix now (a bounded change inside v0's shape, done
in the next unit or PR that touches the area); `v1` means it needs design or a large build (a new tier, a new
store, a new image pipeline, or something that only makes sense once volumes are lineages); `rule` marks a
standing constraint rather than a limitation. Entries are never deleted; a fixed one keeps its id and its row.
Anyone who hits something on v0 sends it to the ledger's owner (`fs-architect`), and it lands here in a small docs
PR; whoever lands a fix says which rows it closes, and the rows flip to `fixed (#PR)`.

Numbers come from the v0 host (`m8id.4xlarge`, us-west-2, NVMe, real S3; `reference_camel_fs_proto_ec2`) unless
the entry says otherwise. "Unit N" refers to the `camelfsd` v0 build units.

ledger's current tail; ids are assigned here. When a fix lands, tell the owner which rows it closes; their status
becomes `fixed (#PR)` and the rows stay.
