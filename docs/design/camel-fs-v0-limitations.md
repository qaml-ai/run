# camelFS v0: the limitations ledger

Miguel, 2026-11-12: "document every limitation or shortcoming or slowness that we encounter for this V0 … on V1 we
address all of these." This is that list, one entry per limitation, kept current as Prototype v0
([camel-fs.md](camel-fs.md) §4) is built and used. Every entry has an id, the area it lives in (`daemon`
`camelfsd`; `jobhost` the TypeScript host agent; `guest` `camel-guest`; `runtime` the Workers/Node backend; `API`
the file API tier and its clients; `S3`; `ops`), what it is, the measured impact with numbers and where they came
from, why v0 accepts it, the v1 fix, and a status (`open` or `fixed`, with the PR when fixed). Entries are never
deleted; a fixed one keeps its id. Anyone who hits something on v0 sends it to the ledger's owner (`fs-architect`),
and it lands here in a small docs PR.

Numbers come from the v0 host (`m8id.4xlarge`, us-west-2, NVMe, real S3; `reference_camel_fs_proto_ec2`) unless
the entry says otherwise. "Unit N" refers to the `camelfsd` v0 build units.

| id | area | what | measured impact | why v0 accepts it | v1 fix | status |
|---|---|---|---|---|---|---|
| L1 | daemon | A checkpoint after a cold (dm-clone-hydrated) mount hashes the **whole** image, because every hydrated region is a private extent and the FIEMAP delta of §1.3 sees it all as "written since the reflink" | 1.6 s for a 2 GiB image on the first checkpoint after a cold mount (unit 3 measurement) | It is paid once per cold mount; the next checkpoints on that host see only real writes. Cold mounts are the minority path (§1.3) | Promote the hydrated file to the image store as the root's canonical copy before the mount's first reflink, so hydrated extents are shared, not private; alternatively diff against the root's chunk map instead of the previous reflink for the first checkpoint | open |
| L2 | daemon | The cold full read uses a 4-deep sequential prefetch on the lazy origin | 3.3 s for a 65 MB tree read cold from S3 (unit 3); `proto/block` measured 40 s for 500 MB with 2,438 nearly serialized GETs at 30–39 ms each | Background hydration, not demand reads, is the cold default for computers and hot images; one-off jobs are the only ones that pay | Unit 4 raises the prefetch to 64 in flight and adds the per-lineage access-pattern prefetch of §1.3; the S3 throughput bound (~1 GB/s hydration) then applies | open (unit 4) |
| L3 | daemon, S3 | The first import of a tree is bounded by S3 PUT rate, one PUT per blob | ~1,460 PUTs/s: 50k files in 37 s (unit 2 measurement) | Imports happen once per lineage (the `/v0/trees` bridge is once per snapshot, incremental after the first) | Pack small blobs into segment objects (the `gitapi` prototype's shape: one PUT per batch, an index of offsets) and read them by range; keeps the content-addressed keys, cuts PUTs ~1,000× for source trees | open |
| L4 | daemon | `Entries()` issues one SQL query per file when enumerating a tree | 50k queries for the large tree; dominates `ls -R`/export of big trees on the SQLite-backed v0 ref store | v0's ref store is SQLite behind the DynamoDB-shaped interface; big-tree enumeration is rare in the dogfood loop | One query per directory (or a single recursive query with the tree's path prefix); with DynamoDB, `BatchGetItem` of subtrees per level | open |
| L5 | daemon | Has-then-Put dedupe does not record a `touch` (§1.9), so an object whose last reference dies during a GC mark could be swept while a new reference is being written | None measurable today: v0 runs the mark only and never sweeps, so nothing can be lost | GC safety is deferred with the sweep itself; the rule is in the design and the mark logs what it would delete | Implement `touch` rows on every skipped write and make the sweep honour touches newer than the mark's start, before the sweep is ever turned on (phase 4) | open (blocks the sweep) |
| L6 | daemon, S3 | A checkpoint uploads chunks with a HEAD then a PUT per chunk, serially per chunk | 130–150 ms for a 7-chunk checkpoint (unit 3): most of it request latency, not bytes | The root publish is off the agent's path (§1.3 step 6) and coalesced every 30 s, so the agent never waits on it | Batch the uploads (16–64 in flight) and drop the HEAD: an unconditional PUT of an immutable object is idempotent and, with `touch`, the dedupe skip is not needed for correctness | open |
| L7 | S3 | No S3 Express One Zone cache tier: every cold chunk GET goes to S3 Standard | A cold job start is ~200–270 ms on Standard against ~53 ms measured on Express (unit 3 comparison) | The host NVMe cache makes the second mount of a lineage on a host free; Express is a second storage class to operate and pay for | Add an Express One Zone bucket as a regional read-through cache in front of Standard for chunks and shards (single-AZ is fine for a cache); measure the hit rate first | open |
| L8 | API, S3 | Search's cold index fetch was measured while `s3speed` may have been saturating the host NIC, so the number is suspect | 2.3 s (Kubernetes) / 4.6 s (Linux) to pull a lineage's shards from S3 before the first query (`proto/search` EC2 run) | The warm numbers (5–25 ms p50) are the ones agents see after the first query on a host; the cold figure only bounds the first | Re-measure on an idle host; if it holds, parallelize the shard fetch and prefetch shards at mount | open (re-measure) |
| L9 | API | API file reads run at S3 speed, one request per file, with no batching and no edge cache (the §1.6 follow-up) | 20–60 ms per file from a Worker; an agent opening twenty files at the start of a turn pays ~0.5–1.2 s | v0 measures the unbatched baseline on purpose (§4, item 8) before adding either | The batched read endpoint on the API tier and the blob-hash-keyed Cloudflare Cache API edge cache (§1.6) | open |
| L10 | API, runtime | Workers' file reads have no hot NVMe path at all: hot speed exists only on hosts | Every API read is a round trip to us-west-2 plus S3 or DynamoDB; the Volume DO used to answer dirty rows in ~0 ms | The design accepts it (§6, question 6) pending the measurement; agents' model calls dwarf it | The edge cache of L9 is the Workers-side equivalent of the host cache; a DO write-back cache in front of camelFS only if the measurement says so | open |
| L11 | ops | Two reliability rules carried from the #869 security review, as standing constraints on every v0 change: **never parse a guest-controlled filesystem as host root** (e2fsprogs/libext2fs on a guest image is a cross-tenant escape surface), and **bound every decompress and unpack** (cap the output at the declared size, reserve the budget before the first byte) | Not a slowness; a rule. The design's checkpoint contract (§1.3) and the delta apply in the guest exist because of the first; the cache budget rule because of the second | They are invariants, not limitations; listed here so that no v0 shortcut (an `e2fsck` on the host "just for the prototype", an uncapped `tar -x`) sneaks in | None needed; v1 keeps them. Any v0 code that violates either is a bug, not a limitation | rule in force |

## How to add an entry

Send the ledger's owner: the area, what you hit, the number and where it came from (host, unit, branch, commit),
and your guess at the v1 fix if you have one. It becomes the next `L<n>` in a small docs PR from `main`. When a
limitation is fixed, its status becomes `fixed (#PR)` and the row stays.
