# Managed Discord bot

The `discord-managed` provider uses one operator-owned Discord application for
all configured servers. Customers invite it and configure their server in the
console. Each installation has at most one tenant binding, with explicit allowed
channels and the existing channel conversation pipeline. The customer-owned
`discord` provider continues to use a separate bot token and Gateway connection.

This integration is disabled by default. The initial release is a pilot with one
Gateway shard. It refuses to connect if Discord recommends more than one shard
or its session-start allowance is exhausted. Multi-shard identify coordination
and an aggregate server dollar budget remain follow-up work. The existing tenant
credit and spending controls still apply, as do the managed server's daily turn
limit and per-sender rate limit. Outbound scheduling is fair between guilds on
each runtime node, with a shared database lock and cooldown for delivery across
nodes. Start with a small pilot and monitor Discord 429 responses.

## Create the platform application

Create separate development and production applications in the
[Discord Developer Portal](https://discord.com/developers/applications), owned by
the Camel team. Record the application ID and public key from General Information,
the OAuth client secret, and the bot token. Keep secret values in the deployment's
secret store, rather than tenant channels or source files.

Enable **Public Bot** and server installation, with `bot` and
`applications.commands` installation scopes. Leave **Requires OAuth2 Code Grant**
off: invite-first installation does not require a Camel account. Request View
Channel, Send Messages, Send Messages in Threads, Attach Files and Read Message
History; do not request Administrator. The invite generated by the console uses
permission bitfield `274878008320` and guild installation context `0`.

Register the OAuth redirect URI exactly as:

```text
<AGENT_PUBLIC_URL>/console/discord/callback
```

Account linking uses a separate authorization-code grant with `identify guilds`
scopes and a single-use state bound to the console session and account. The
callback's server ID is only context: configuration verifies current Discord
management permissions and the bot's server membership independently. Linked
tokens are encrypted and valid for at most fifteen minutes in the runtime; users
reauthorize before later management changes. See
[Discord OAuth2](https://docs.discord.com/developers/topics/oauth2).

The Gateway requests `GUILDS`, `GUILD_MESSAGES` and `DIRECT_MESSAGES`. Leave the
privileged Message Content, Server Members and Presence intents off. Direct
bot-user mentions supply message content without the Message Content intent.
See [Discord Gateway](https://docs.discord.com/developers/events/gateway).

## Configure runtime secrets

Set `AGENT_DISCORD_MANAGED_ENABLED=true` and
`AGENT_DISCORD_MANAGED_SECRET_ARN` to a Secrets Manager secret containing:

```json
{
  "applicationId": "<Discord application ID>",
  "botToken": "<Discord bot token>",
  "clientSecret": "<Discord OAuth client secret>",
  "publicKey": "<64-character hex Discord public key>"
}
```

For development, use the four corresponding plain
`AGENT_DISCORD_MANAGED_APPLICATION_ID`, `_BOT_TOKEN`, `_CLIENT_SECRET` and
`_PUBLIC_KEY` variables instead. Do not mix plain values with the ARN. The runtime
also needs console authentication, an encryption key for channels, a public URL,
and Postgres. Startup applies the additive managed Discord migration.
See [Configuration](configuration.md).

Restart all runtime nodes after credential rotation. Rotating the bot token
invalidates existing connections; update the platform secret and restart the
fleet so the new Gateway owner connects with the replacement token. Rotating the
console session secret also invalidates encrypted short-lived Discord links;
administrators must reconnect their Discord account.

## Enable setup interactions

Once the runtime serves the configured application, set the Interactions Endpoint
URL in Discord to:

```text
<AGENT_PUBLIC_URL>/channels/discord-managed/interactions
```

The endpoint verifies Discord's Ed25519 signature against the exact request body
and timestamp, answers signed PING requests, and rejects invalid signatures with
401. `/camel setup` answers immediately with an ephemeral setup link, without a
model call. See [interaction endpoint configuration](https://docs.discord.com/developers/interactions/overview)
and [interaction response timing](https://docs.discord.com/developers/interactions/receiving-and-responding).

Register the application command once through Discord's API using the platform
bot credential. Use `POST /api/v10/applications/<applicationId>/commands` with
this body; POST updates the existing command of the same name, preserving other
application commands:

```json
{
  "name": "camel",
  "description": "Configure Camel for this Discord server",
  "type": 1,
  "default_member_permissions": "32",
  "integration_types": [0],
  "contexts": [0],
  "options": [
    { "name": "setup", "description": "Open the Camel server setup console", "type": 1 }
  ]
}
```

The runtime does not register commands automatically. Discord command visibility
is only a convenience; the console rechecks administration permissions on every
configuration change. See
[application commands](https://docs.discord.com/developers/interactions/application-commands).

## Pilot checks

Use two test servers connected to different Camel accounts. Complete one install
from the console and one invite before signup. A mention before setup should
produce a setup link with no agent or model usage; earlier messages must not run
after configuration. Select one test channel per server, configure distinct
prompts and tools, then verify actual mentions, attachments, tool execution and
account usage attribution.

Confirm a non-administrator cannot claim a server, a server already bound to
another account returns a conflict, and an expired Discord authorization cannot
change policy. Check a thread of an allowed channel, a disallowed channel, a role
mention, and a direct message. Pausing or disconnecting should stop pending sends;
removal should pause routing, while a temporary unavailable guild should recover
without being treated as removal. Re-invitation requires explicit reactivation.
An already accepted agent turn may finish and incur usage after pause or removal;
its managed Discord reply is suppressed. Pause does not abort active agent turns.

Review `discord_managed_*` events for Gateway ownership, retries, routing errors
and installation changes, plus existing channel delivery failures. Saved
configuration and a connected Gateway are separate from a delivered reply.
Before broad rollout, validate shard coordination and cross-node rate-limit
behavior, and complete Discord's current application verification requirements.
